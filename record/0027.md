# Record 0027

Repair: three hand-written records had overwritten auto-generated enactment stubs.

§21.5 has `enact()` write `record/<NNNN>.md` itself, auto-numbered, carrying one line —
the citation it enacted and why. That is what makes the enactment's own commit satisfy
VPS 2/4/5 without ceremony. A human writing a record by hand picks the next number by
looking at the directory, and if an enactment has since taken that number the write is a
silent overwrite: the file still looks like a valid record, so nothing complains, and the
only evidence that a ruling was ever enacted disappears.

That happened here. The live shopping-list run filed [2026] VPS 22, 23 and 24 while this
session was working, taking record slots 0019, 0020 and 0021. Prose written for 0019 and
0020 destroyed the stubs for VPS 22 and 23.

Both stubs are restored from history and the prose moved to 0025 and 0026. All 22 rulings
in the book now have an enactment stub; a test asserts that from now on, because the
failure mode is silent and the loss is of exactly the evidence the record exists to hold.

Two things worth saying plainly. The constitution caught this: the commit was DENIED citing
VPS 2, because overwriting an existing record means `recordsAdded` is zero and a kernel
change then has nothing explaining it. The rule fired for the reason it was written. And
the underlying sharp edge remains — there is no `foundry record` command, so the next hand
-written record picks its number the same way. A helper that allocates the next free number
would remove the edge entirely; until it exists, check `ls record/` against `foundry book`
before writing one by hand.
