# Record 0032

The drift check answered a narrower question than record/0020 claimed.

record/0020 introduced a digest list in `foundry doctor` and described it as guarding the
correspondence between this vendored kernel and canonical upstream. It does not do that. The
digests were recorded FROM these same files, so the check detects local tampering — someone
editing `lean/Vps/` here — and is silent about upstream moving. Those are different questions
and only one was being asked.

It surfaced immediately. The canonical kernel was parameterised today (upstream record/0005:
the sovereign digest becomes an argument, so one engine can serve many jurisdictions), which
diverged `Legitimacy.lean` and `Proofs.lean`. The digest check passed throughout, because
nothing here had been edited. The vendored copy is simply behind.

`doctor` now asks both questions and distinguishes them: PASS/FAIL on local edits, and a
separate WARN when the vendored copy is behind canonical. The second is a warning rather
than a failure because being behind is the expected steady state while VPS is vendored at
all — which is the condition record/0020 already gave a demolition date.

That demolition date has arrived in one place: the Vibe Justice System now consumes the
kernel as a pinned lake dependency and vendors nothing, which is exactly what the digest
parameterisation was for. Foundry can follow, and when it does both the digest list and this
warning are deleted rather than maintained.

The general lesson is worth more than the fix: a check whose reference values come from the
thing it is checking cannot detect that the thing has drifted from anything external. It can
only detect that the thing has changed since the check was written. Saying which of those a
guard provides is part of writing it.
